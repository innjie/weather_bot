- (2026-08-14) 빌드 도구: Gradle(Kotlin DSL) + Gradle Wrapper 8.14.5 채택. 최초 로컬에 설치된 Gradle 9.7.0으로 wrapper를 생성했으나, Shadow 플러그인(8.3.6, fat jar 빌드용)이 Gradle 9의 `application` 플러그인 API 변경(`mainClassName` 제거)과 충돌해 `mainClassName does not exist` 오류 발생. Shadow 9.x는 베타뿐이라 안정성을 위해 Kotlin 2.2.0/Shadow 8.3.6과 검증된 Gradle 8.14.5로 wrapper를 재생성해 해결.
- (2026-08-14) 패키지 구조: `com.weatherbot` 루트 아래 `config`(환경변수 로딩), `weather`(`WeatherProvider` 인터페이스)부터 시작. `bot`, `scheduler`, `db` 패키지는 해당 기능 구현 시점에 추가 예정.
- (2026-08-14) 주요 의존성 버전(Maven Central 최신 안정 버전 기준 확정): JDA 5.6.1, kotlinx-coroutines 1.10.2, Exposed 0.61.0(1.0.0-beta 계열은 API 변경 폭이 커서 제외), sqlite-jdbc 3.49.1.0, kotlinx-serialization-json 1.9.0, logback-classic 1.5.18, dotenv-kotlin 6.5.1(토큰/API 키 하드코딩 방지용 `.env` 로딩).
- (2026-08-14) DB 스키마: 알림은 길드(서버)의 특정 채널로 발송되므로 사용자 단위가 아닌 길드 단위로 `guild_configs` 테이블 하나만 설계 (guild_id, channel_id, location, weather_provider, notify_hour/minute). 길드당 설정 1건만 허용(`guild_id` unique). 다중 스케줄/이력 테이블은 현재 요구사항에 없어 제외(YAGNI). `Table` 정의는 `com.weatherbot.db.GuildConfigTable`.
- (2026-08-15) `DatabaseFactory` 구현: `BotConfig.dbPath`(`.env`의 `DB_PATH`, 기본값 `./data/weather_bot.db`)로 하드코딩 없이 경로 설정. 앱 시작 시 상위 디렉토리 없으면 생성 후 `Database.connect()`로 SQLite 연결, `SchemaUtils.create(GuildConfigTable)`로 테이블 부재 시 생성. `Main.kt`에서 JDA 초기화 전에 `DatabaseFactory.init()` 호출. `./gradlew run`으로 실제 실행해 `guild_configs` 테이블 및 unique index 생성을 확인.
- (2026-08-15) `KmaWeatherProvider` 구현: 기상청 단기예보(getVilageFcst) + 에어코리아 시도별 실시간 측정정보(getCtprvnRltmMesureDnsty)를 JDK 내장 `HttpClient`로 호출(새 HTTP 라이브러리 의존성 추가 없음). 지역명→격자좌표(nx,ny)/시도명 매핑은 `src/main/resources/kma_grid.json`으로 코드와 분리해 관리(주요 도시 18곳, 재빌드만으로 추가/변경 가능하도록 설계). 단기예보는 최대 3일치만 제공하므로 `getWeeklyForecast`는 현재 조회 가능한 일자만 반환하고, 7일 전체 지원(중기예보 API 연동)은 "주간날씨 요약" TODO 항목에서 별도 처리하기로 함. API 키 미보유로 컴파일 검증까지만 진행, 라이브 호출 테스트는 추후 실제 키 발급 시 수행.
- (2026-08-16) `OwmWeatherProvider` 구현: OpenWeatherMap Geocoding API(`/geo/1.0/direct`)로 지역명을 위도/경도로 변환 후, 5일/3시간 간격 예보(`/data/2.5/forecast`) + 대기오염(`/data/2.5/air_pollution`) API를 조합. KMA와 달리 별도 좌표표 없이 지오코딩으로 처리해 지역 확장이 더 유연하나 요청마다 API 호출이 하나 더 필요함(트레이드오프로 인지). 미세먼지는 PM10 농도(µg/m³)를 한국 환경부 등급 기준(좋음 0~30/보통 31~80/나쁨 81~150/매우나쁨 151~)으로 변환해 KMA 구현체와 동일한 라벨 체계를 사용, 두 Provider 간 사용자 응답 포맷 일관성 유지. 오전/오후 날씨는 3시간 간격 데이터 중 09시/15시대(없으면 인접 시간대)를 사용. API 키 미보유로 컴파일 검증까지만 진행.
- (2026-08-16) 설정 커맨드(`/날씨설정`) 구현: `SlashCommand` 인터페이스 + `CommandListener`(이름 기반 라우팅)로 향후 커맨드 추가가 용이한 구조로 설계. 알림 채널은 별도 파라미터 없이 커맨드 실행 채널로 자동 지정해 UX 단순화. `데이터소스=기상청` 선택 시 `KmaGridTable`로 즉시 지역 유효성 검증(로컬 조회, API 호출 없음), OpenWeatherMap은 지오코딩이 유연해 사전 검증 생략(실제 알림 발송 시점에 실패 가능성 존재, 추후 필요시 보완). DB 접근은 신규 `GuildConfigRepository`(upsert)로 일원화. 커맨드는 글로벌로 등록(`jda.updateCommands()`)하며, 전파까지 최대 1시간 소요될 수 있음. 토큰 미보유로 실제 로그인/커맨드 등록/인터랙션 테스트는 보류, 컴파일 검증까지만 진행.
- (2026-08-16) "오늘날씨" 커맨드(`/오늘날씨`) 구현: `WeatherProviderFactory`(provider 코드→구현체 생성)와 `WeatherMessageFormatter`(`DailyWeather`→한국어 메시지, JDA 비의존)를 `weather` 패키지에 분리해 이후 스케줄러의 자동 알림에서도 그대로 재사용 가능하도록 설계. 슬래시 커맨드는 동기 API라 `suspend fun`인 `WeatherProvider` 호출을 위해 `BotScope`(전역 코루틴 스코프)에서 `event.deferReply()` 후 followup으로 응답. 길드 설정이 없으면 `/날씨설정` 안내 후 종료. 토큰 미보유로 컴파일 검증까지만 진행.
- (2026-08-16) "도시날씨" 커맨드(`/도시날씨`) 구현: 길드 설정(`guild_configs`)과 무관하게 독립 동작. 위치/데이터소스 옵션은 `/날씨설정`과 동일한 패턴, 조회/응답 로직은 `/오늘날씨`와 동일하게 `WeatherProviderFactory`/`WeatherMessageFormatter`/`BotScope`를 재사용. 토큰 미보유로 컴파일 검증까지만 진행.
- (2026-08-16) `NotificationScheduler`(자동 알림 스케줄러) 구현: OS cron이 아닌 앱 내부 코루틴으로 매 분 정각까지 `delay` 후 `guild_configs` 전체를 조회해 `notify_hour`/`notify_minute`이 현재 시각과 일치하는 길드만 알림 발송. 길드별로 독립된 코루틴(`BotScope.scope.launch`)에서 처리해 한 길드의 API 실패/지연이 다른 길드 알림에 영향을 주지 않도록 설계. 채널 조회는 `JDA.getChannelById(MessageChannel::class.java, ...)` 사용, 채널을 찾지 못하거나 날씨 조회가 실패해도 예외를 잡아 로그만 남기고 스케줄러 자체는 계속 동작하도록 함. `Main.kt`에서 `jda.awaitReady()` 이후 `NotificationScheduler(jda).start()` 호출. 토큰 미보유로 컴파일 검증까지만 진행, 실제 알림 발송 및 분 단위 타이밍 정확도는 추후 실기기 테스트 필요.
- (2026-08-16) secure coding 점검 및 개선: 두 가지 이슈 발견 후 수정. (1) `CommandListener`/`TodayWeatherCommand`/`OtherCityWeatherCommand`의 예외 처리에서 `e.message`를 그대로 Discord 응답에 노출하던 부분을 일반화된 안내 메시지로 변경(상세 예외는 `logger.error`로만 기록). 특히 `TodayWeatherCommand`/`OtherCityWeatherCommand`는 `deferReply()`가 비-ephemeral이라 내부 오류 상세가 채널 전체에 노출될 수 있었음(OWASP 정보노출 지양 원칙). (2) `KmaApiClient`/`AirKoreaApiClient`/`OwmGeocodingClient`/`OwmForecastClient`/`OwmAirPollutionClient` 5개 HTTP 클라이언트 모두 요청 타임아웃이 없어 외부 API 응답 지연 시 스레드/코루틴이 무기한 대기할 수 있었던 문제를 `HttpClient.connectTimeout` + `HttpRequest.timeout()` (각 10초)으로 해결. `KmaGridTable.find` 등 사용자에게 실제로 유용한 안내(지원 지역 목록 등)를 담은 커스텀 예외 메시지는 기존과 동일하게 유지(별도 catch에서 사전 검증).

## 인프라
- (2026-08-14) 배포 환경: 저가 VPS/클라우드에서 상시 구동 (Docker + `restart: always`). 알림이 매일 정해진 시각에 발송되어야 하므로 로컬/개인 PC 구동은 배제.
- (2026-08-16) Docker 빌드/구동 검증: `docker build`로 멀티스테이지 이미지(gradle shadowJar → JRE 런타임) 빌드 성공 확인. 실제 토큰 없이 검증하기 위해 gitignore된 임시 `.env`(더미 값)로 `docker compose up` 실행 → (1) `DatabaseFactory`가 컨테이너 내에서 정상적으로 SQLite 초기화, (2) 유효하지 않은 토큰에 대해 JDA가 `InvalidTokenException`을 던지고 앱이 exit code 1로 깔끔히 종료(먹통/NPE 없음), (3) `restart: always` 정책에 따라 재시도 루프가 도는 것까지 확인 — 실제 배포 시 반드시 유효한 `DISCORD_TOKEN`이 필요함을 재확인. `docker-compose.yml`의 `env_file: .env`는 `.env` 파일이 없으면 `docker compose` 자체가 실행되지 않으므로, 배포 전 `.env.example`을 `.env`로 복사해 실제 값을 채워야 함(정상 동작, 문서화만 필요). 테스트에 사용한 임시 `.env`와 테스트 이미지(`weather-bot-test`)는 검증 후 모두 삭제.
- (2026-08-14) 소스 저장소: GitHub `innjie/weather_bot` public 저장소로 연결. `gh auth login` 시 발급된 fine-grained PAT(`github_pat_...`)는 저장소 생성 권한이 없어 실패했고, `repo` 스코프를 포함한 OAuth 토큰(`gho_...`)으로 브라우저 재로그인 후 `gh repo create`로 생성/push 성공. 이후 push 시 macOS 키체인에 캐시된 예전 PAT 때문에 403이 발생해 `gh auth setup-git`으로 자격증명을 gh 토큰으로 재등록해 해결.
